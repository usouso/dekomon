# 全ゲーム共通の開発・独立レビュー標準
版: 1.1 / 統括: dot

## 目的と適用
ユーザーは重要な方針を決め、dot は担当・優先度・証拠・停止条件を管理する。制作、独立レビュー、修正、再テストを、既に承認された範囲で進める。同じAIの自己レビューだけで開発を完了にしない。

この文書・[レビュー手順](REVIEW-PROCEDURE.md)・[引継ぎ書式](HANDOFF-TEMPLATE.md)を、既存および今後のゲームの共通ルールとする。各プロジェクトの入口で制作担当と異なる独立担当を明記し、不在なら「未確保」と記録する。

## 着手前と重複防止
1. repo、branch、基準commit、未コミット変更、制作中作業、予約済み作業、LOCK、既存の引継ぎを確認する。
2. 同一対象の制作を重複起動しない。既存担当が制作中なら、隔離した読取りやレビュー準備を進める。
3. task ID、担当、目的、基準commit、更新時刻、次の担当、停止理由を台帳に記す。古いLOCKを期限だけで削除しない。
4. 既存のPRレビューと受渡し経路を優先する。新APIキー、スケジューラー、権限設定を必要だと決めつけない。
5. 秘密情報、認証ファイル、キー、トークン、個人の会話やPCの記録を、公開証拠に含めない。

## 1往復の流れ
1. 制作担当が対象commit、変更理由、再現手順、既存テスト、既知制約を渡す。
2. 独立担当が差分と関連コードを読み、必要なテストを実行する。旧commitの指摘解消と、新headの再レビューを区別する。
3. 実ゲームの起動、画面確認、通常入力による進行をそれぞれ試す。ソースを読んだ「仮想プレイ」は設計検討として記録する。
4. 指摘を再現手順、期待、実測、重要度、証拠とともに制作担当へ渡し、受領確認を残す。文書の保存だけを受渡し成功にしない。
5. 制作担当が修正し、別担当が修正commitで同じ条件を再テストする。問題がなければ、問題を作って修正実績を増やさない。
6. 同一指摘の修正・再テストは原則3回まで。重大問題、証拠不足、独立担当不在、権限不足が残ればその工程を停止し、別の承認済み準備を続ける。

## 実操作と自動検査
タイトル → 開始/種類選択 → 選択 → 戦闘 → 結果 → 次の選択または周回終了を通常入力で通す。自動モード、debug直行、ページ内の状態書換えによる検証とは分ける。

自動検査は、例外/pageerror、要求周回未完、計算不一致、重なり/はみ出し、透け、点滅過多、規定サイズのスクロール違反を終了コードへ反映する。数値や表を出すだけで合否判定を済ませない。

自動検査の終了0は、その検査が扱った範囲の結果。実画面と通常入力の独立確認を代用しない。必要な実行環境がなければ、実際のエラーと「環境制約」を記す。

## 工程と証拠
呼出し、コードレビュー、テスト、実ゲーム起動、画面、通常入力/進行、結果受渡し、修正、別担当の再テストを別々に「未実施 / 合格 / 失敗 / 環境制約」で記録する。

各記録に担当、対象commit、日時、手順、実測、証拠を添える。seed・画面寸法・入力方式、stdout/stderr・終了コード、スクリーンショット等を対象commitと結ぶ。予定、設定済み、過去の実績を今回の合格にしない。報告の伝言受領と、証拠ファイルの読了も分ける。

全必須工程の証拠がそろうまで、開発完了にしない。公開、merge、自動公開、課金、新規ログイン、永続アクセス・ネットワーク・権限拡大は、別途明示された承認の範囲だけで行う。

## 新規プロジェクトへ
1. このフォルダーの標準・手順・引継ぎ書式と Initialize-GameProject.ps1 を取得する。
2. dot が新プロジェクトの担当と対象範囲を指定する。承認済みの既存フォルダーに対して `Initialize-GameProject.ps1 -ProjectPath <絶対パス>` を実行するか、3文書を docs/game-development/ へコピーする。
3. repo rootのAGENTS.md・CLAUDE.mdから、そのrepo内の標準へ相対リンクを置く。既存の無関係な指示は保持する。異なる既存文書を自動で上書きしない。
4. 制作・独立担当それぞれが実際に読んだ版、パス、対象commitを返す。リンク検査だけで別AIの読了を推定しない。
5. 小さな実対象で受渡しと独立再検証を1往復してから実働と報告する。

各クラウドcheckoutもrepo内の入口から読む。draft PRへの保存だけでは、mainをcloneする既存の制作工程に適用されたことにならない。
